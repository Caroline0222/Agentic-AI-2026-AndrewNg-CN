# 用代码作为行动 Planning with code execution

**核心思想：与其让 LLM 输出 JSON 再解析，不如直接让它写 Python 代码来表达计划——代码天生擅长描述多步骤、复杂逻辑的行动。**

上一节让 LLM 用 JSON 描述计划。但仔细想想，JSON 只能表达"调哪个工具、传什么参数"，表达不了循环、条件判断、变量复用。与其让 LLM 输出 JSON 再解析，不如直接让它写代码。

---

## 一、JSON 的局限

处理复杂数据查询时，JSON 的短板很明显。

**场景一：** 用户问"哪个月份热巧克力销量最高？"如果只提供基础工具（取最大值、过滤行），Agent 需要一个极其冗长的工具调用序列：过滤热巧克力 → 按月分组 → 每组求和 → 取最大值 → 返回月份。每一步都是一次独立的工具调用，JSON 来回传递，既慢又容易出错。

**场景二：** 用户问"上周有多少风险交易？"又需要一套全新的工具组合。每遇到新的复杂查询，就得不断创建新的定制工具——这种方法脆弱且低效。

如果允许 LLM 直接写代码，用 Pandas 一行 `df[df.product=='hot chocolate'].groupby('month')['sales'].sum().idxmax()` 就搞定了，不用来回调工具。

---

## 二、代码执行的三个优势

**利用大型库。** LLM 可以直接使用 Pandas、NumPy、Matplotlib 这些数据处理库里成百上千个内置函数。这些库已经把复杂的数据操作封装好了，Agent 不需要自己从头实现。

**高表达能力。** 代码天生擅长描述多步骤、复杂逻辑的计划——解析日期、按日期排序、过滤、去重、计数，几行代码搞定。JSON 要表达同样的逻辑，需要拆成很多步独立的工具调用，每步都要模型重新推理一次。

**性能更优。** 多篇论文和工程实践表明，让 LLM 直接写代码的性能优于写 JSON 再解析 [1]：

| 来源 | 数据 |
|---|---|
| HuggingFace GAIA 基准 | 代码动作比 JSON 工具调用**少 30% 步骤**，困难基准准确率更高 |
| Cloudflare Code Mode | 简单任务省 32% token，复杂多步骤任务省 **81% token** |
| smolagents 15,724 轨迹分析 | 2.4% 的轨迹第一次调用出现解析错误；有解析错误的成功率 42.3% vs 无错误的 51.3%，**差 21.3%** |

> HuggingFace smolagents 团队的原话很直白："我们专门制作了编程语言来擅长表达由计算机执行的操作。如果 JSON 片段是更好的方式，这个包本应以 JSON 片段编写。" [2]

代码比 JSON 强的地方在于**控制流**：循环、条件判断、错误处理、变量复用。JSON 是单拍的（一次调一个工具），代码可以在一次动作里完成多步逻辑。搜索三个话题然后汇总结果，JSON 方式需要三轮工具调用，代码方式一个 for 循环就搞定。

## 三、怎么实现

### 提示词设计

明确要求 LLM 编写代码来解决用户的查询，以 Python 代码返回，用标签包裹：

```
请编写 Python 代码解决用户的查询。
将代码放在 <execute_python> 和 </execute_python> 标签之间。
```

### 执行流程

1. LLM 输出包含 `<execute_python>...</execute_python>` 标签的文本
2. 用正则表达式提取标签之间的代码
3. 在执行环境中运行这段代码
4. 获取执行结果
5. 将结果回传给 LLM，生成最终回复

### 与反思结合

代码执行失败时（SyntaxError、运行时错误），把错误信息回传给 LLM，让它反思并生成修正后的代码。通常一两次迭代就能得到正确结果。这正是 Module 2 Reflection 模式跟代码执行的天然结合点。

## 四、安全风险与沙箱

直接运行 LLM 生成的代码有真实风险。

**真实案例：** Andrew Ng 团队成员使用的一个高度自主的代码执行器，曾错误执行了 `rm *.py` 命令，删除了项目目录中的所有 Python 文件。幸运的是该成员有 GitHub 仓库备份，没有造成实际损失——但如果没有备份，后果会很严重 [3]。

**最佳实践：必须在沙箱中运行。**

| 沙箱方案 | 启动速度 | 隔离级别 | 适合场景 |
|---|---|---|---|
| **E2B** | 秒级 | 轻量虚拟机 + 容器，边界硬 | 快速验证、低频调用、不想管基础设施 |
| **Docker** | 镜像已拉取时毫秒级 | 内核 namespace + cgroup，容器级 | 高频批量执行、私有化部署、数据敏感场景 |
| **直接 exec()** | 即时 | 无隔离 | **不要在生产环境用** |

> 选型原则：数据敏感（金融、医疗、企业内部）→ Docker 自建，数据不出网；低频交互式（网页对话里让 Agent 算个数据）→ E2B，按秒计费省运维 [4]。

## 五、规划模式总结

到这里，Planning 设计模式的三种实现方式都讲完了：

| 方式 | 5.x 节 | 怎么表达计划 | 适合场景 |
|---|---|---|---|
| 自然语言 | 5.1 | LLM 直接讲出步骤 | 快速原型，不追求可靠执行 |
| JSON 结构化 | 5.2 | JSON 列表，每步含 tool + arguments | 需要可靠解析、工具调用明确的场景 |
| 代码执行 | 5.3 | 直接写 Python 代码 | 复杂数据处理、需要控制流的场景 |

Planning 模式的核心权衡：**放弃一些控制权，换取显著更大的能力范围。** 开发者无法预先知道 LLM 会生成什么样的行动序列，这是缺点——但大多数时候，这种灵活性带来的能力扩展是值得的。

该模式下 LLM 可以生成一个详细的"构建清单"并逐步执行复杂任务。随着基础模型智能程度不断提高，完全由 Agent 控制流程的 AI 系统的场景越来越多。难点始终在工具设计和流程设计上，不在代码量上。

---

**总结**

- JSON 只能表达"调哪个工具、传什么参数"，表达不了循环、条件、变量复用；代码天生擅长这些
- 三个优势：利用大型库（Pandas/NumPy）、高表达能力（几行代码替代多轮工具调用）、性能更优（少 30% 步骤，复杂任务省 81% token）
- 实现流程：提示词要求写代码 + 标签包裹 → 正则提取 → 沙箱执行 → 结果回传 → 可与反思结合修正错误
- 安全风险真实存在（rm *.py 案例），必须在沙箱（E2B / Docker）中运行，生产环境别用 exec()
- 规划模式三种实现：自然语言（5.1）→ JSON 结构化（5.2）→ 代码执行（5.3），按场景选
- 核心权衡：放弃控制权换取能力范围，大多数时候值得
