# 规划设计模式 Planning workflows

**核心思想：让 LLM 自己决定执行复杂任务需要调哪些工具、按什么顺序调，开发者只提供工具集，不硬编码调用序列。**

复杂软件系统需要工厂模式、单例模式、依赖倒置这些设计模式和原则来管理复杂度。Agent 系统也一样，想要实现复杂度与效率并重，也需要设计模式。本节介绍 Planning（规划）设计模式。

---

## 一、什么是 Planning 模式

Planning 模式的 Agent 高度自主，能自行决定执行复杂任务所需的工具调用序列，无需事先硬编码。

这跟 Module 3 讲的简单工具使用不一样。简单工具使用是用户问一个问题，模型决定调一个工具（或串联调几个），路径基本是预设的。Planning 模式是模型面对一个复杂请求，先自己规划一个多步执行计划（调哪些工具、按什么顺序、每步的输入依赖上一步的什么输出），再逐步执行。

学术界把 Agent 控制流分成两种主要模式 [1]：

| 模式 | 怎么工作 | 适合什么任务 |
|---|---|---|
| **ReAct**（Reason+Act） | 思考一步 → 调一个工具 → 看结果 → 再思考一步 → 再调……循环 | 下一步依赖上一步结果，路径不可预知 |
| **Plan-and-Execute** | 先一次性规划完整计划，再逐步执行 | 长链条、多步骤复杂任务，计划可审查可改 |

Planning 模式就是 Plan-and-Execute：规划是显式的一步，人可以审查、可以改，计划埋在明面上而不是藏在 token 流里。

## 二、案例：客服助理 Agent

目标：构建能回答广泛、复杂查询的智能体，在运行时灵活决定采取哪些行动。比如客户问"你们有没有库存中售价低于 100 美元的圆形太阳眼镜？"

### 提供工具集

给 LLM 一套功能工具：

| 工具名 | 功能 | 示例用途 |
|---|---|---|
| `get_item_descriptions` | 获取商品描述或元数据（名称、款式、材质、颜色、形状等） | 用户说"round sunglasses"时查出所有带"round"特征的太阳眼镜 |
| `get_item_price` | 查询指定商品的价格 | 找到商品后判断哪些低于 $100 |
| `check_inventory` | 检查商品是否有库存及数量 | 找到圆形眼镜后查询是否在库 |
| `check_past_transactions` | 查看用户历史交易记录 | 客户支持场景，如"我上周买的眼镜有问题" |
| `process_item_sale` | 处理购买行为，创建销售订单 | 用户确认要买时执行交易 |
| `process_item_return` | 处理退货操作 | 用户想退货时发起退货请求 |

### LLM 编写计划

用户问"库存中售价低于 100 美元的圆形太阳眼镜"，LLM 根据请求返回一个逐步执行计划：

1. 调用 `get_item_descriptions` 找"round sunglasses"
2. 根据步骤 1 的输出（找到的产品），调用 `check_inventory` 查库存
3. 对库存有货的结果，调用 `get_item_price` 检查哪些低于 $100
4. 输出最终结果

注意这个计划是 LLM 自己生成的，开发者没有硬编码"先调 A 再调 B 再调 C"。面对不同的用户问题，LLM 会生成不同的计划。

### 逐步执行

按照计划，将每一步的指令和上一步的输出/上下文依次喂给 LLM，让它调用相应的工具并执行。每一步的工具返回结果会作为下一步的输入。

### 最终输出

所有步骤执行完毕后，将结果汇总反馈给 LLM，生成最终的用户答案——比如"我们库存中有 3 款圆形太阳眼镜售价低于 $100：款式 A（$85）、款式 B（$72）、款式 C（$95）"。

## 三、好处

Planning 模式的 Agent 有几个明显好处：

**扩展了任务范围。** Agent 拥有丰富的能力组合，能处理开发者没预料到的复杂请求。用户问"库存中低于 $100 的圆形太阳镜"和"我上周买的眼镜想退货"是两种完全不同的任务，但同一套工具 + 同一个 Agent 都能处理，因为路径是 LLM 现场规划的。

**灵活性和自主性。** 开发者无需事先编排工具调用的确切序列。只要工具设计合理，Agent 面对新问题能自己组合出合理的执行路径。

**代码量小。** 开发者只需要写工具函数 + 一个让 LLM 规划和执行的循环，不用写大量的 if-else 分支逻辑。难点集中在工具设计和流程设计，不在代码量。

---

## 四、风险

Planning 模式的风险也很实在：

**运行时不可预知。** 开发者无法预知 LLM 会生成什么样的计划。大多数时候计划是合理的，但偶尔会生成出人意料的调用序列——调错工具、漏调关键步骤、或者调了不该调的工具。

**出错和越权风险。** 如果工具集里包含 `process_item_sale`（执行交易）或 `process_item_return`（发起退货）这类有副作用的工具，LLM 可能在不该调的时候调了它们。一个客户只是问问库存，Agent 却自作主张下了单——这种越权在实际部署中是不能接受的。

**收敛控制。** 复杂任务里 LLM 可能陷入"思考-调用-思考-调用"的长循环，迟迟不给最终答案。需要设置 `max_steps` 上限和"无进展检测"（连续几轮没有推进主目标就降级或转人工）[2]。

> 对有副作用的工具（交易、退款、删除、对外发布），工程上通常强制 Human-in-the-Loop：Agent 只准备草案，人确认后才真正执行 [2]。

## 五、现状：AI Coding 成功，其他领域尝试中

Planning 模式在 AI Coding（AI 编程）应用中非常成功——Cursor、Windsurf、Claude Code 这些工具让 LLM 自主规划"读文件 → 改代码 → 跑测试 → 修 bug"的执行序列，效果很好。原因之一是代码任务的反馈循环天然闭环（跑测试就知道对不对），容错空间大（改错了可以再改）。

在其他领域（客服、运维、金融操作）仍然处在尝试阶段。这些领域的任务容错空间小，越权代价高，对可预测性和可审计性的要求远高于代码场景。

随着基础模型智能程度不断提高，完全由 Agent 控制流程的场景越来越多。这种模式的灵活度高、代码量小，难点在工具设计与流程设计上。

## 六、工具设计的经验判断

同一个场景，不同经验的开发者会设计出完全不同的工具集：

| 开发者经验 | 工具数量 | 典型做法 | 问题 |
|---|---|---|---|
| 经验丰富 | 3 个核心工具 | 每个工具封装好复杂逻辑，粒度合适 | — |
| 经验不足 | 10+ 个工具 | 过度抽象，每个工具只做很小的事 | LLM 选择困难，计划过长，容易出错 |
| 经验不足 | 1-2 个基本工具 | 直接暴露数据库 session 给 AI 自己写代码 | **极其不安全**，SQL 注入、越权访问、数据泄露 |

工具设计是 Planning 模式里最吃经验的部分。好的工具抽象遵循几个原则：

- **粒度合适。** 一个工具做一件完整的事（如"查商品描述"），不做半个事（如"查数据库表"），也不做十件事（如"查商品 + 查库存 + 查价格"全塞一个工具里）
- **副作用明确。** 只读工具（查询类）和写操作工具（交易、退货、删除）要清楚区分，写操作必须有人工确认环节
- **权限隔离。** 永远不要把数据库 session 或底层 API 直接暴露给 LLM——这是把数据库钥匙交给了模型，它可能写出任何 SQL，包括删表

## 七、框架推荐：smolagents

如果你要上手 Planning 模式，推荐 Hugging Face 社区的 smolagents 框架 [3]。

smolagents 的几个特点：

- **核心代码约 1000 行**，抽象少，开发者容易看懂，方便重写其中的逻辑做定制化
- **工具开发简单**，用 `@tool` 装饰器定义一个工具即可，不用写复杂的 schema
- **代码智能体（Code Agent）**：模型输出的动作是可直接执行的 Python 代码片段，官方称比传统 JSON 工具调用方式少约 30% 的步骤和 LLM 调用 [3]
- **支持 E2B 沙盒**，代码执行隔离在安全环境里
- **兼容多种 LLM**（OpenAI、Anthropic、HuggingFace Hub 上的模型），通过 LiteLLM 统一接口
- **有流程跟踪功能**，可以看到 Agent 每一步的思考和工具调用

GitHub 约 2.9 万 star，Apache-2.0 许可，2026 年 5 月发布 v1.26.0，维护活跃 [3]。

> 选框架不是选最重的，是选最合适的。smolagents 的定位是"极简但够用"，适合理解 Planning 模式的内部逻辑，也适合快速搭原型。生产环境如果需要更强的编排能力（分布式、多 Agent 协作、复杂状态管理），再考虑 LangGraph 或 AutoGen 这类重框架。

---

**总结**

- Planning 模式让 LLM 自主决定工具调用序列，开发者只提供工具集，不硬编码路径
- 跟 ReAct 的区别：Planning 先规划完整计划再执行（适合长链条复杂任务），ReAct 走一步看一步（适合路径不可预知的任务）
- 客服助理案例：6 个工具 + LLM 现场规划 4 步计划 + 逐步执行 + 汇总输出
- 好处：扩展任务范围、灵活自主、代码量小，难点在工具设计和流程设计
- 风险：运行时不可预知、出错越权、长循环不收敛。有副作用的工具必须 Human-in-the-Loop
- 现状：AI Coding 场景成功（反馈闭环天然、容错空间大），其他领域仍在尝试
- 工具设计吃经验：粒度合适 + 副作用明确 + 权限隔离。永远别把数据库 session 直接暴露给 LLM
- smolagents 框架推荐：Hugging Face 开发，约 1000 行核心代码，代码智能体少 30% 步骤，适合上手和理解内部逻辑
