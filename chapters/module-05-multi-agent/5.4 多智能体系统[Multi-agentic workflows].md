# 多智能体系统 Multi-agentic workflows

**核心思想：把一个什么都干的巨型 Agent 拆成多个专注不同角色的子 Agent，像团队分工一样协作完成复杂任务。**

尽管所有 Agent 可能都基于同一个底层 LLM，运行在同一台电脑上，但将复杂任务分解成多个独立的角色或进程是一种更有效的开发方法，就像团队协作或计算机的多线程/多进程一样。

---

## 一、为什么要拆

想象你有一个复杂的 AI 业务系统：LLM 需要调用十几种甚至几十种工具，在一段几千字的提示词指导下运行，一个典型业务流程要走七八步。

这种"一个 Agent 干所有事"的设计有几个问题：

- **提示词臃肿。** 几千字的系统提示词覆盖所有场景，模型注意力被稀释，每个具体任务的执行质量都受影响
- **上下文爆炸。** 多轮工具调用的中间结果全堆在一个上下文窗口里，很快就撑满 128K
- **难以迭代。** 改一个功能要动整个提示词，牵一发动全身

把一个 Agent 拆成多个子 Agent，构成 Multi-Agent 系统，这些问题就缓解了。下图是一个市场 Agent 拆分的例子——拆出调研、生成报表、创建文件三个子 Agent，各干各的。

## 二、五个优势

### 标准三个

**任务分解。** 像人类团队一样，将复杂任务自然地分解为拥有不同角色和技能的子任务。研究员负责调研，设计师负责视觉，写手负责文案——每个 Agent 只做自己擅长的事。

**专注性。** 开发者一次只专注构建一个特定角色。你要做的只是把"平面设计师 Agent"做到最好，不用操心它会不会做市场调研。单个 Agent 的任务越简单，完成效果越好。

**模块化与复用。** 一个通用的"平面设计师 Agent"可以用于营销手册，也可以用于社交媒体帖子。组件化了就能复用。

### 补充两个

**突破上下文限制。** 现在绝大多数模型有 128K 上下文，对于需要多轮规划执行的调研类任务或业务分析任务来说完全不够。但如果让每个 Agent 只负责自己的部分，最终只返回调研结果给一个总结 Agent，就能规避上下文限制——总结 Agent 不必在上下文里存储其他 Agent 的调研过程，它只看结果就够了。Anthropic 把这叫"上下文压缩"：子 Agent 在自己的窗口里翻了一百页资料，最后只把几段精华交回主管 [1]。

**节约成本。** 资金成本上，每次请求都附带大量上下文非常烧钱，即使命中缓存。Multi-Agent 体系里每个 Agent 上下文都比较短，更节约 token 费用。时间成本上，上下文越短 LLM 回复越快，延迟越低；多个 Agent 还能并行处理任务，进一步压缩时间。Anthropic 的数据：lead agent 并行启动 3-5 个 subagent、每个 subagent 并行调用 3+ 个工具，复杂查询的研究时间最多缩短 90% [1]。

## 三、Anthropic 的工程数据

Anthropic 在 2025 年 6 月公开了 Claude Research 多 Agent 系统的完整工程报告 [1]，数据很有参考价值：

| 指标 | 数据 |
|---|---|
| 多 Agent vs 单 Agent（Opus 4 + Sonnet 4 子 Agent vs 单 Opus 4） | 内部研究评测高 **90.2%** |
| Token 用量解释性能差异 | **80%**（三个因素解释 95%） |
| 普通 Agent token 消耗 | 约聊天的 **4 倍** |
| 多 Agent 系统 token 消耗 | 约聊天的 **15 倍** |
| 并行工具调用缩短研究时间 | 最多 **90%** |

> Anthropic 的核心结论：多 Agent 系统起作用的主要方式是"花足够的 token 来解决问题"。token 用量解释了 80% 的性能差异——多 Agent 架构通过多个独立上下文窗口，把 token 消耗能力扩展到单 Agent 的天花板之上 [1]。

## 四、怎么创建不同的 Agent

通常通过**提示词 + 工具**的组合来创建不同角色的 Agent。

以市场分析 Agent 为例：
- **提示词**：告诉 LLM 它具有高超的市场分析技巧，描述市场分析的范式与最佳实践
- **工具**：配备网页浏览工具，让它可以自己做市场调研

每个 Agent 的"专业化"就是 prompt + 工具 + 模型的组合 [2]。更进一步，可以用不同档位的模型做不同的事——主 Agent 负责规划与综合用 Opus，路由与简单筛选用 Haiku/Sonnet mini，深度推理用 Opus。这种分级搭配能把"所有环节都吃 Opus 预算"的浪费省下来，成本可降 30-50% [3]。

## 五、代价和局限

Multi-Agent 不是万能的，有三个显性代价：

**Token 消耗成倍上升。** 15 倍聊天 token 意味着同一笔预算，Multi-Agent 能跑的任务数是单 Agent 的 1/15。任务价值不够高，这笔开销很难被结果覆盖。研究型任务、跨系统自动化任务的"决策价值"高，能承担溢价；客服问答、文档摘要这类轻量任务用 Multi-Agent 反而是亏本买卖。

**协调复杂度。** Agent 越多，任务边界、交接格式、状态保存和失败重试就越难设计。Anthropic 的早期版本曾给简单查询派出 50 个子 Agent，或者让多个子 Agent 重复搜索同一方向。一个子 Agent 的错误输出可能被主 Agent 当成事实继续汇总，错误沿着链路放大 [1]。

**排查难度。** 多 Agent 系统的运行路径不固定，同一个输入可能走出不同路线。日志和追踪不完整时，很难判断问题出在模型、工具、提示还是任务拆分。

**三条规矩避免乱套** [4]：

1. 任务拆解要互不重叠——给每个子 Agent 的目标尽量正交，才能真正并行
2. 沟通走结构化摘要——子 Agent 只交精华结论和证据，不交流水账
3. 预算和终止条件要提前定——每个任务的工具调用次数封顶，不设上限会成本失控

## 六、什么时候不该用 Multi-Agent

Anthropic 自己划了适用边界 [1]：

| 适合 Multi-Agent | 不适合 Multi-Agent |
|---|---|
| 重并行、可大量同时探索的任务 | 大多数编码任务（可并行性低） |
| 信息量超过单个上下文窗口 | 需要所有 Agent 共享同一上下文 |
| 对接大量复杂工具的高价值任务 | Agent 之间依赖很强的任务 |
| 研究型任务（方向多、路径不可预知） | 客服问答、文档摘要等轻量任务 |

> 一个判断标准：任务价值够不够高、能不能大量并行、信息量是不是超过单窗口。三条都满足才值得用 Multi-Agent，否则单 Agent 更简单更便宜。

---

**总结**

- 把一个什么都干的巨型 Agent 拆成多个专注角色的子 Agent，像团队分工一样协作
- 五个优势：任务分解 / 专注性 / 模块化复用 / 突破上下文限制（上下文压缩）/ 节约成本（短上下文 + 并行）
- Anthropic 数据：多 Agent 比单 Agent 高 90.2%，代价是 15 倍 token 消耗；token 用量解释 80% 性能差异
- 创建不同 Agent = 提示词 + 工具 + 模型的组合；模型分级（Opus 做推理 / Haiku 做路由）可降 30-50% 成本
- 三个代价：token 成倍上升 / 协调复杂度 / 排查难度。三条规矩：任务不重叠 / 结构化摘要 / 预算封顶
- 适用边界：高价值 + 重并行 + 信息超单窗口才值得用；编码任务和轻量任务别用
