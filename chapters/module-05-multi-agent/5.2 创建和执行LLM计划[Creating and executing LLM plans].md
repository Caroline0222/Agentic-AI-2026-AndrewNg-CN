# 创建和执行 LLM 计划 Creating and executing LLM plans

**核心思想：让 LLM 以 JSON 格式输出计划，下游代码才能可靠解析、逐步执行。**

上一节让 LLM 直接讲出自己的任务规划，但自然语言不够清晰和明确，难以被下游代码稳定地解析和执行。本节解决这个问题——要求 LLM 以结构化格式（JSON）输出计划。

---

## 一、为什么需要结构化输出

自然语言描述计划有个根本问题：同一个意思可以有一百种说法。LLM 说"先查一下圆形太阳镜的库存"，下游代码怎么知道这对应哪个工具、参数是什么？写正则去匹配关键词？那遇到"检查一下圆框眼镜还有没有货"就匹配不到了。

结构化格式（JSON 或 XML）能清楚地界定计划的步骤、所需工具及其参数，让下游代码可靠地解析每个步骤，系统性逐步执行。

---

## 二、怎么实现

### 提示词设计

开发者在系统提示词里这样写：

> 你可以访问以下工具，并需要以 JSON 格式创建一个分步计划。

同时详细描述所需的 JSON 结构，列出可用工具的名称和参数说明。

### JSON 结构

LLM 返回一个 JSON 列表，列表中的每个对象代表一个步骤，包含三个键值：

| 字段 | 含义 | 示例 |
|---|---|---|
| `description` | 步骤描述（给人看的） | "查找圆形太阳镜" |
| `tool` | 要调用的工具名称 | `get_item_descriptions` |
| `arguments` | 传递给工具的参数 | `{"shape": "round", "category": "sunglasses"}` |

### 完整示例

以 5.1 的客服助理为例，用户问"库存中售价低于 100 美元的圆形太阳镜"，LLM 返回的计划：

```json
[
  {
    "description": "查找圆形太阳镜",
    "tool": "get_item_descriptions",
    "arguments": {"shape": "round", "category": "sunglasses"}
  },
  {
    "description": "检查库存",
    "tool": "check_inventory",
    "arguments": {"items": "$step_1_result"}
  },
  {
    "description": "查询价格筛选低于100的",
    "tool": "get_item_price",
    "arguments": {"items": "$step_2_result", "max_price": 100}
  }
]
```

### 执行流程

下游代码的执行逻辑很简单：

1. 接收 LLM 的字符串输出
2. 用 `json.loads()` 转成 JSON 对象
3. 遍历每个步骤，提取 `tool` 和 `arguments`
4. 调用对应的工具函数，传入参数
5. 将每步结果作为下一步的上下文

这个解析器写起来非常方便——核心就是一个 `json.loads()` 加一个循环，比写正则匹配自然语言稳定得多。

## 三、结构化输出的四级保证阶梯

让 LLM 输出 JSON 有不同的保证强度，按可靠性从低到高排成四级 [1]：

| 级别 | 方法 | 保证什么 | 不保证什么 |
|---|---|---|---|
| **第 1 级** | 提示词贴样例 | 无任何保证，失败自己兜 | 一切 |
| **第 2 级** | JSON 模式 (JSON Mode) | 输出是合法 JSON | 字段名、类型、结构对不对 |
| **第 3 级** | Strict Schema (Structured Outputs) | 符合你定义的 JSON Schema | 值在语义上对不对 |
| **第 4 级** | 加应用侧语义校验 | 结构对 + 语义对 | — |

**第 2 级的坑值得点名：** OpenAI 的 JSON 模式只保证输出是合法 JSON，不保证任何字段。模型可能返回一个合法 JSON 但字段名全不对，或者该有的字段缺失。它是给"我只要能 `json.loads`"的场景准备的过渡档，不是给 Agent 用的。

**第 3 级保证的是语法合规，不是语义正确。** 模型返回的 JSON 字段都在、类型都对，但值可能是错的——比如日期填了过去的、评分超出了业务范围、或者用户闲聊了一句模型硬编造了一个符合 schema 的回答而不是拒收 [1]。Gemini 文档说得最直白：输出是符合 schema 的合法 JSON，但"始终在你的应用里校验值"。

**第 4 级才是生产可用的终点。** 即使有 Structured Outputs 的保证，仍然要做应用侧语义校验：日期范围、业务逻辑约束、字段间的一致性。约束解码消灭的是解析失败，不是内容失败。

## 四、生产环境的三个失效模式

即使用了 Structured Outputs，生产环境仍有三个常见失效模式 [2]：

**静默截断。** 这是最危险的——看起来成功了，实际是坏的。当 `max_tokens` 在生成中途耗尽，模型停止产生 token，输出是一个不完整的 JSON（缺少闭合括号、字符串中途断开）。`finish_reason` 是 `"length"` 而不是 `"stop"`。解决方法：解析前先检查 `finish_reason`，如果是 `"length"` 就别解析，用更大的 `max_tokens` 重试或拆成更小的调用。

**Schema 复杂度故障。** 受限解码在 token 级别强制执行 Schema，但复杂 Schema（4 层以上嵌套、50+ 字段）会让模型生成质量下降，约束压力随嵌套复合 [1]。如果需要提取大量字段，拆成多个聚焦的提取调用，别塞一个巨型 Schema。

**格式限制拖累推理。** 2024 年有研究（*Let Me Speak Freely?*）发现：给模型的输出加格式限制，会明显拖累复杂推理任务的表现 [3]。直觉上也好理解——逼模型先吐 `{"name":` 这个开头，等于让它还没想清楚就先承诺了结构。

> 实操原则：**先推理，后 JSON。** 需要推理的任务，让模型先自由思考再进入 Schema；纯抽取任务可以放心全开格式限制 [3]。

---

## 五、现代方法：Structured Outputs

2024 年 8 月 OpenAI 推出 Structured Outputs，保证模型输出 100% 符合你定义的 JSON Schema [4]。Anthropic 也在 2025 年底发布了原生结构化输出。所有主要供应商对语法和结构无效的 JSON 故障率已降至 0.3% 以下 [2]。

使用方式（以 OpenAI Python SDK 为例）：

```python
from pydantic import BaseModel
from openai import OpenAI

class PlanStep(BaseModel):
    description: str
    tool: str
    arguments: dict

client = OpenAI()
resp = client.beta.chat.completions.parse(
    model="gpt-4o-2024-08-06",
    messages=[{"role": "system", "content": "创建一个分步执行计划..."}],
    response_format=list[PlanStep],
)
plan = resp.choices[0].message.parsed  # 直接拿到 PlanStep 对象列表
```

用 Pydantic 定义 Schema，SDK 自动处理解析，不需要自己写 `json.loads()` 加错误处理。这是目前最推荐的方式——第 3 级保证由供应商在解码层强制执行，开发者只需补第 4 级语义校验。

---

**总结**

- 自然语言计划难以被下游代码稳定解析，结构化 JSON 输出是 Planning 模式可靠执行的基础
- JSON 结构三字段：`description`（给人看）、`tool`（工具名）、`arguments`（参数）
- 执行流程：接收字符串 → `json.loads()` → 遍历步骤 → 调用工具 → 结果作为下一步上下文
- 四级保证阶梯：提示词样例 → JSON 模式 → Strict Schema → 应用侧语义校验。第 4 级才是生产终点
- 三个失效模式：静默截断（检查 finish_reason）、Schema 复杂度故障（拆小）、格式限制拖累推理（先推理后 JSON）
- 现代方法：OpenAI Structured Outputs / Anthropic 原生结构化输出，Pydantic 定义 Schema，供应商在解码层保证合规
