# 四种设计模式与工程实践 [Design Patterns and Engineering]

**核心思想：四种设计模式各解决一类问题，先掌握什么时候用，再深入怎么搭。**

这一节把四种 Agentic 设计模式落成一个「什么时候用」的判断框架，并说明为什么 Agentic 工作流值得投入、工程实践的关键能力是什么。

---

## 四、四种设计模式：先掌握「什么时候用」(Design Patterns)

| 设计模式（Design Pattern） | 解决什么问题 | 企业价值 | 对应模块 |
|---|---|---|---|
| Reflection（反思） | 首次结果不够好 | 自动检查、修正 | Module 2 |
| Tool Use（工具使用） | 模型自身缺乏信息/执行能力 | 访问数据、API、搜索、代码 | Module 3 |
| Planning（规划） | 步骤复杂且不能一次完成 | 拆解并执行多步骤任务 | Module 5 |
| Multi-Agent（多智能体） | 单个 Agent 职责过多 | 专业分工、并行协作 | Module 5 |

客户提出「我们想做 Agent」时，先判断他真正缺的是哪一种能力：

- 缺信息 → Tool Use
- 缺质量控制 → Reflection
- 缺复杂流程管理 → Planning
- 缺专业分工/规模 → Multi-Agent

这比直接画一张「多 Agent 架构图」更有效。

---

## 五、为什么值得：扩大任务边界 (Why It Matters)

传统 LLM 是「一次理解 → 一次生成」；Agentic 工作流是「理解 → 分解 → 获取信息 → 执行 → 检查 → 修改 → 再执行」。

因此它特别适合：

- 复杂研究
- 多步骤分析
- 知识密集型工作
- 需要外部信息的任务
- 需要多轮验证的任务
- 需要跨系统执行的业务流程

吴恩达课程把发票处理（invoice processing）、客服（customer service）、研究报告（research/report writing）列为典型应用 [1]。一个实用的判断标准是：如果一个任务本身就要求一个熟练员工连续完成多个步骤，它通常比「一问一答」式任务更值得采用 Agentic 工作流。

### 五个场景判断问题

| # | 问题 | 判断 |
|---|---|---|
| ① | 任务是否多步骤？（multi-step） | 一步能完成，通常不必 Agentic |
| ② | 中间步骤是否需要判断？（judgment） | 全是确定性规则，传统 Workflow 更可靠 |
| ③ | 是否需要外部信息或工具？（external data/tools） | 需实时数据/系统/搜索/计算，价值明显提高 |
| ④ | 结果是否值得迭代？（iterative gain） | 可通过检查与修改显著提升，Reflection 很有价值 |
| ⑤ | 能否定义「成功」？（success criteria） | 说不清「怎样算完成得好」，这个 Agent 很难做好 |

## 六、工程实践：Evals 与错误分析 (Engineering Practice)

系统化的评测（Evals）与错误分析（Error Analysis），是有效构建 Agentic AI 的关键能力 [1]。

效果要通过闭环来验证：

> Build → Observe → Analyze Errors → Improve → Evaluate → Repeat

### 评估的六个维度

| 维度 | 要确认什么 |
|---|---|
| Task Success | 任务到底有没有完成 |
| Quality | 结果是否达到业务标准 |
| Reliability | 相同任务是否稳定 |
| Safety / Compliance | 有没有越权、泄密、错误操作 |
| Cost | 完成一次需要多少调用 / Token / 工具调用 |
| Latency | 业务是否能接受 |

Agent 是一个系统，评估对象是整个工作流能否可靠完成业务任务，单次模型输出只是其中一个环节。

### 先观察真实失败，再建立 Evals

起步阶段先跑通、后沉淀，指标是逐步长出来的：

1. 先把 MVP 跑起来
2. 观察真实失败案例
3. 把失败归类（信息提取错误 / 工具调用错误 / 判断错误 / 输出格式错误 / 合规问题 / 不必要的调用 / 没完成任务）
4. 把高频、高风险错误变成 Eval
5. 每次改系统，重新跑

这样就形成一个可持续的 Agent Engineering Loop（工程闭环）。

---

**总结**

1. **四种模式先掌握「什么时候用」**：缺信息 → Tool Use；缺质量控制 → Reflection；缺流程管理 → Planning；缺分工/规模 → Multi-Agent。
2. **Reflection 提供质量控制回路（Generate → Evaluate → Improve）**，最终质量仍需 Evals 兜底。
3. **工具使用（Tool Use）让 LLM 从「生成答案」拓展到「获取信息 + 调用系统 + 执行动作」**，是业务流程自动化的起点。
4. **效果靠数据判断**：通过 Build → Observe → Error Analysis → Eval → Improve 闭环持续改进。
