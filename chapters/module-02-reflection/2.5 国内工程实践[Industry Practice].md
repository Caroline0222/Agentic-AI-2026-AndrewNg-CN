## 九、国内工程实践：从课程到产品 (Industry Practice)

国内云厂商已经把反思的思路做成了可配置的能力。这一节从产品接口、提示词优化、工作流实现三个层次补充 [8][9][10]。

### 产品接口：反思作为可配置组件

阿里云通义 UI Agent 的 PC 端接口中，反思被设计为可配置的 Agent 角色，并提供对应模型配置字段，包括是否添加反思 Agent（enable_reflector）以及反思 Agent 使用的模型（reflector_model）等 [8]。生成、执行、评审这些职责能映射到产品接口。

阿里云新版智能体应用（Agent 2.0）展示「规划—执行—反思」链路，记录工具调用入参与返回结果，并设置工具调用轮次上限 [8]。保留执行记录、给循环设置预算，对应上一节的停止条件。

### 提示词优化：区分两种修改对象

阿里云的 Prompt 自动优化文档描述利用输入输出样例和评测数据，对提示词进行多轮评估、反思和优化 [8]。这和运行时修订是两回事：

| 对照项 | 当前任务的输出反思 | 提示词自动优化 |
|---|---|---|
| 修改对象 | 当前邮件、代码或报告 | 后续任务使用的提示词 |
| 反馈对象 | 本次输出中的问题 | 提示词在评测样本上的表现 |
| 交付物 | 修订后的任务结果 | 优化后的提示词模板 |

一个是「改这一次的结果」，一个是「改以后所有任务的模板」。前者是运行时能力，后者是配置优化。客户问「反思能帮我优化什么」时，先分清他要的是哪一种，报价和交付边界完全不同。

### 工作流实现：生成器与反思器

腾讯云开发者社区的教程展示了完整实现：配置内容生成器，配置独立的反思器提示词，把反馈交回生成器，用 LangGraph 连接节点和状态，用条件分支结束循环 [9]。

百度智能云的文章用三个角色解释反思流程：执行者（Actor）生成初始输出，评估者（Evaluator）检查是否符合要求，自我反思模型（Self-Reflection Model）分析问题并生成改进建议；循环在达到预期要求或迭代次数上限时结束 [10]。

---

**总结**

1. **反思在产品里是可配置组件**：enable_reflector / reflector_model 等字段让生成、执行、评审职责映射到产品接口。
2. **运行时反思和提示词离线优化是两回事**，前者改当前结果，后者改模板，报价和交付边界不同。
3. **国内云厂商的实现印证了课程方法论**：规划—执行—反思链路、工具调用轮次上限、生成器—评估器循环都已落地。
