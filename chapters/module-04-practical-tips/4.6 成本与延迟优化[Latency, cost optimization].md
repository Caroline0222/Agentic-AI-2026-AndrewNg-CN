# 成本与延迟优化 Latency, cost optimization

**核心思想：先测每一步花了多少时间和多少钱，找到最贵最慢的那一步，针对性优化。**

系统输出质量达到要求后，下一个优化重点是延迟和成本。但要强调优先级：**质量优先，延迟次之，成本最后。**

对早期团队来说，高质量输出比延迟和价格重要得多。Andrew Ng 在课程里反复讲这一点——他见过很多团队先急着优化成本和延迟，结果系统本身还没跑顺。正确的节奏是：等系统运行良好之后，才把精力转向延迟优化；只有当系统有了大量用户、成本成了实际问题之后，才是集中优化成本的时机。

> 一个判断标志：成本成为问题往往是个"好问题"——说明你的系统有大量用户在用。到这一步才值得花精力优化成本。

---

## 一、延迟优化

优化延迟的关键是**计时基准测试（Timing Benchmark）**，找出工作流里的瓶颈。

### 计时分析

详细记录工作流中每个步骤的耗时。以课程里的研究 Agent 为例：

| 步骤 | 耗时 |
|---|---|
| LLM 生成搜索词 | 7 秒 |
| 网页搜索 | 5 秒 |
| LLM 抓取来源 | 3 秒 |
| 网页抓取 | 11 秒 |
| LLM 写文章 | 18 秒 |
| **总计** | **44 秒** |

### 定位瓶颈

看时间线就能判断哪些环节有最大优化空间。这个例子里，"写文章"18 秒占了大头，"网页抓取"11 秒排第二。这两个环节值得优先优化，前面的"LLM 抓取来源"3 秒不值得花时间改。

### 优化手段

**并行化（Parallelism）。** 把可以独立进行的步骤并行执行。比如网页抓取多个网页时，不要排队一个个抓，同时抓取，总时间从"所有网页抓取时间之和"变成"最慢那个网页的抓取时间"。Anthropic 在 Claude Research 多 Agent 系统的工程报告里提到，引入并行工具调用后，复杂查询的研究时间最多砍了 90% [3]。

**更换 LLM。** 尝试更小、更快的模型（可能稍不智能），或者测试不同的 LLM 提供商，找到返回 token 最快的服务。有些服务商有专用硬件加速特定任务，速度差异很明显。

> 注意：并行化降低的是 wall time（用户等待的总时间），但总计算成本可能不变甚至增加——多个并行分支的 token 消耗都要付钱。降延迟和降成本可能冲突，后面会讲。

## 二、成本优化

优化成本的关键是**成本基准测试（Cost Benchmark）**，找出最贵的步骤。

### 成本计算

计算工作流中每个步骤的平均成本。不同组件的计费方式不同：

| 组件类型 | 计费方式 | 举例 |
|---|---|---|
| LLM | 按输入和输出的 Token 长度收费 | GPT-4o 输入 $2.50/百万 Token，输出 $10.00/百万 Token |
| API 工具 | 按调用次数收费 | 搜索 API 每次调用 $0.01 |
| 计算/服务 | 按服务器容量和服务费计算 | 向量检索按实例时长计费 |

### 定位瓶颈

把每一步的成本算出来，找出成本贡献最大的组件。比如一个工作流里 PDF 转文本这一步花了 $0.03/次，远高于其他步骤的 $0.001/次——这就是成本瓶颈。

### 优化手段

**换更便宜的组件或 LLM。** 这是成本优化最直接的方式：

- 用小模型替换大模型（在质量允许的前提下）。微调一个 7B 模型在特定任务上匹配 70B 模型的效果，每次查询成本可降 10-50 倍
- 换更便宜的 API 提供商。同样的搜索能力，不同服务商价格差异可能很大
- 对高频查询做缓存。OpenAI 和 Anthropic 都支持 Prompt Caching——系统提示词部分只在首次请求时计费，后续命中缓存可节省 50-90% 的系统提示词成本 [2]

**压缩上下文。** 多轮对话的历史消息会越堆越长，输入 token 线性增长。每隔几轮对历史做摘要压缩，可以把输入 token 减少 40-60% [2]。但要注意：压缩可能丢失关键上下文，导致模型决策质量下降——必须用评估指标验证压缩后的效果没有退化。

## 三、两个容易踩的坑

实际做延迟和成本优化时，有两个坑要避开：

**坑一：只看平均值，不看分布。** 延迟是分布，不是单值。p50（中位数）代表常见体验，p95/p99 暴露长尾——有些请求因为排队、重试、工具超时，耗时可能是 p50 的 5-10 倍。只看平均值会漏掉长尾问题。一个实际案例：用户反馈回答慢，开发者一直以为是 LLM 生成慢，打开链路追踪才发现 LLM 只花了 2 秒，向量库检索花了 4 秒——瓶颈在向量库，不在模型 [3]。

**坑二：只算单次调用成本，不算 verified success 成本。** 一个便宜但低成功率、高重试率的模型，每个成功任务的实际成本可能比贵但稳定的模型更高。成本要按 verified success 归一：

```
每个成功任务的成本 = (模型成本 + 工具成本 + 计算成本 + 重试成本) / 成功任务数
```

如果优化降低单次调用成本，但让成功率从 90% 掉到 70%，重试次数翻倍，整体成本反而上升。优化前必须固定质量基线，验证优化后质量没有退化。

## 四、延迟与成本的权衡

延迟和成本优化有时冲突，最典型的例子是**并行化**：

| 优化手段 | 对延迟的影响 | 对成本的影响 |
|---|---|---|
| 并行化工具调用 | 降（wall time 减少） | 可能升（并行分支都要付费） |
| 换更小更快的模型 | 降（响应快） | 降（便宜） |
| Prompt Caching | 微降（减少重复计算） | 降（重复部分省钱） |
| 压缩上下文 | 降（输入 token 少） | 降（输入便宜） |
| 减少检查点 | 降（省持久化时间） | 降（少算钱）但崩溃恢复成本升 |

并行化是唯一可能"降延迟但升成本"的手段。Anthropic 的多 Agent 数据很说明问题：一般 Agent 对话大约用掉 4 倍聊天的 token，多 Agent 系统是 15 倍 [3]。用并行架构放大 token 预算换来速度提升，值不值取决于任务价值——高价值、可大量并行的任务适合，简单任务别动用并行舰队。

---

**总结**

- 优先级：质量优先，延迟次之，成本最后。等系统跑顺、有大量用户后再优化成本
- 延迟优化：计时基准测试找瓶颈 → 并行化独立步骤 → 换更快模型或提供商
- 成本优化：成本基准测试找最贵步骤 → 换便宜组件 → Prompt Caching → 压缩上下文
- 延迟是分布不是单值，看 p50/p95/p99，别只看平均值
- 成本按 verified success 归一，便宜但低成功率的模型可能更贵
- 延迟和成本可能冲突：并行化降 wall time 但可能增加总 token 成本
