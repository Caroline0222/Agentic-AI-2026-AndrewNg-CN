# 组件级评估 Component-Level Evals

**核心思想：把要改的那一步单独拎出来评估，切断后续步骤的干扰，信号更清晰、成本更低。**

上一节通过错误分析确定了要改进的单个组件（比如网页搜索）。下一步就是为这个组件单独建一套评估，针对性调优。

---

## 一、为什么端到端评估不够

端到端评估（End-to-End Evaluation）测的是整个工作流的最终输出。它最接近用户体验，但有两个硬伤：

**成本高。** 哪怕只是换了搜索引擎这种小改动，也要重新跑完整个工作流（搜索 → 筛选 → 写初稿 → 反思 → 修订），每一次都消耗 token 和时间。调参 10 次就是 10 倍成本。

**噪声掩盖信号。** 假设你优化搜索让召回率提升了 5%，但最后一步写初稿的 LLM 这次恰好发挥失常，最终文章依然很差。你看一眼最终结果，会误判"搜索优化没效果"——其实是后续组件的随机性把你的增量改进盖住了。

组件越多的工作流，这个问题越严重。每多一个 LLM 调用，就多一层随机噪声。

---

## 二、组件级评估是什么

组件级评估（Component-Level Evaluation）把单个组件从完整工作流里切出来，单独测试它的输出质量。类比传统软件测试：

| | 传统软件测试 | Agent 评估 |
|---|---|---|
| 端到端测试 | 集成测试 (Integration Test)（整个系统跑一遍） | 端到端评估（完整工作流最终输出） |
| 组件级测试 | 单元测试 (Unit Test)（单个函数测一遍） | 组件级评估（单个组件输出评分） |

组件级评估的关键操作：**切断后续步骤。** 比如评估网页搜索组件时，搜索一出结果就直接评分，不跑后续的筛选、写初稿、反思那些步骤。这样后续 LLM 的随机性完全不会干扰你的评估信号，token 成本也大幅降低。

还有一个好处：**团队分工。** 如果多个团队分别负责不同组件（搜索团队、生成团队、检索团队），每个团队可以自行维护自己组件的评估指标，互不阻塞。

## 三、案例：研究 Agent 的网页搜索

接上一节，错误分析表明研究 Agent 遗漏关键点的问题主要出在网页搜索组件。现在为它建组件级评估。

### 步骤一：建黄金标准网页清单

针对少数几个测试查询（比如"黑洞的最新研究""西雅图租金趋势"），请人类专家提前人工搜索，确认哪些网址是最高质量、最权威的答案来源。这些被人工确认的优质网址就是黄金标准（Golden Standard）。

```
查询：黑洞的最新研究
黄金标准：
  - https://nasa.gov/blackholes-research-2025
  - https://arxiv.org/abs/2401.xxxxx
  - https://nature.com/articles/blackhole-observation
  - https://space.com/black-hole-breakthrough
```

不需要很多查询，3 到 5 个就够起步，每个查询单独维护一份黄金标准清单。

### 步骤二：写代码算 F1 分数

当 Agent 执行搜索时，它会返回一堆网页链接。不需要让人或 LLM 去读这些链接，直接写代码对比"Agent 搜出的链接"和"黄金标准清单"的重叠程度。

这里用的是信息检索领域的标准指标——F1 分数（F1 Score），它综合了两个维度：

| 指标 | 含义 | 公式 | 衡量什么 |
|---|---|---|---|
| **精确率 Precision** | 搜出来的结果里，有多少是对的 | 搜出的正确链接数 / 搜出的总链接数 | 搜出来的是不是太杂（噪声多） |
| **召回率 Recall** | 黄金标准里，有多少被成功搜出来 | 搜出的正确链接数 / 黄金标准总链接数 | 该找到的有没有漏掉 |
| **F1 分数** | 两者的调和平均 (Harmonic Mean) | 2 × (P × R) / (P + R) | 综合准确性和全面性 |

**为什么要看两个维度而不只看一个：** 只看精确率，Agent 可能只返回 1 个链接而且是对的，精确率 100%，但漏掉了另外 3 个黄金标准链接——召回率只有 25%。只看召回率，Agent 返回 100 个链接把黄金标准全包进去，召回率 100%，但 99 个是噪声——精确率只有 1%。F1 分数逼着两个维度都兼顾。

### 步骤三：用指标快速调参

有了 F1 分数这个指标，可以快速尝试各种调参方向，每次只跑搜索组件，几秒钟出结果：

| 调参方向 | 具体操作 | 看什么指标变化 |
|---|---|---|
| 换搜索引擎 | 从 Google 切到 Bing 或 Tavily | F1 是否提升 |
| 调结果数量 | top-5 → top-10 → top-20 | 召回率涨但精确率可能跌，F1 权衡 |
| 调日期范围 | 只搜近 1 年 vs 近 3 年 | 是否能找到最新权威资源 |
| 加关键词 | 查询加"research""paper""2025" | 精确率是否提升 |

这种迭代速度是端到端评估做不到的——端到端跑一次要几十秒到几分钟，组件级几秒就出结果。

## 四、组件级评估与端到端评估的配合顺序

两种评估配合使用，有明确的先后顺序：

1. **端到端评估**：先跑整体，发现系统表现不佳（比如研究文章漏掉关键点）
2. **错误分析**：拆开 Trace 定位病根，发现主要问题在网页搜索组件
3. **组件级评估**：为网页搜索建黄金标准 + F1 指标，快速调参迭代
4. **组件优化**：在组件级评估指导下改进（换引擎、调参数）
5. **回到端到端评估**：验证组件改进确实提升了整体性能

```
端到端评估（发现问题）→ 错误分析（定位组件）→ 组件级评估（快速调优）→ 组件优化 → 端到端评估（验证整体提升）
```

最后一步不能省。组件级 F1 涨了不代表最终用户体验一定提升——可能搜索结果变好了但后续 LLM 不会用这些结果。组件级评估负责"快速迭代"，端到端评估负责"最终验收"。

---

## 五、评测的四个层次（扩展）

组件级和端到端只是其中两层。完整的 Agent 评测体系有四个层次，各有职责：

| 层次 | 测什么 | 成本 | 定位精度 | 用途 |
|---|---|---|---|---|
| **Step-level（步骤级）** | 单次 LLM 调用、单次工具选择是否合理 | 最低 | 最准 | 调 Prompt、验证工具调用逻辑 |
| **Component-level（组件级）** | 检索质量、上下文组装、记忆读写等子系统 | 低 | 准 | 调参、换组件、增量改进 |
| **End-to-End（端到端）** | 完整任务最终是否完成、质量如何 | 高 | 最难归因 | 发布验收、生产监控 |
| **Online（在线）** | 生产流量 (Production Traffic) 采样、A/B 实验 (A/B Testing)、用户反馈 | 最高 | 反映真实分布 | 校准前三层、发现线上问题 |

实践原则：**从上往下建，从下往上 debug。** 用户抱怨发生在端到端层，但归因往往要下沉到组件层甚至步骤层才能找到真因。

判定方式的升级原则：**能用规则就别用 LLM judge，能用 judge 就别用人。** 越靠前的越便宜、越可复现，只在确有必要时才升级判定方式。比如 F1 分数是纯代码规则（链接集合比对），成本几乎为零；LLM-as-Judge 用于无法规则化的主观判断（文章质量）；人工评审只留少量高价值样本做校准锚点。

---

**总结**

- 端到端评估成本高、噪声大，组件级评估切断后续步骤干扰，信号更清晰、迭代更快
- 组件级评估 = 单元测试类比：把单个组件拎出来单独测，几秒出结果
- 黄金标准 + F1 分数是信息检索组件的标准评估方法：Precision 管精度，Recall 管召回，F1 综合两者
- 配合顺序：端到端发现问题 → 错误分析定位组件 → 组件级快速调优 → 回到端到端验证整体提升
- 完整评测体系四层：Step / Component / E2E / Online，从上往下建、从下往上 debug
- 判定方式升级原则：能用规则就别用 judge，能用 judge 就别用人
