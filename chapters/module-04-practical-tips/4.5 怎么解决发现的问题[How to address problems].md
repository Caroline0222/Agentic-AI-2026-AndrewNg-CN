# 怎么解决发现的问题 How to address problems

**核心思想：评估找到问题后，按"先简单后复杂"的顺序改——调参数比换组件快，改提示词比换模型快，换模型比微调快。**

跑了评估、做了错误分析、定位到问题组件之后，就进入实际改进阶段。本节讲的是：对于不同类型的组件，有哪些改进手段，以及怎么选。

---

## 一、非 LLM 组件的改进

网页搜索、RAG 检索、代码执行、传统 ML 模型这类组件，改进手段比较直接：

**调参数或超参数。** 这是最快的改进方式，不改组件本身，只调它的配置：

| 组件 | 可调参数 | 调什么 |
|---|---|---|
| 网页搜索 | 结果数量、日期范围、语言过滤 | 多召回 vs 少噪声的权衡 |
| RAG 检索 | 相似度阈值、分块大小 (Chunk Size)、Top-K | 召回率 vs 精确率 |
| 代码执行 | 超时时间、内存限制、沙盒配置 | 安全性 vs 灵活性 |
| 传统 ML（如目标检测） | 置信度阈值 | 误报 (False Positive) vs 漏报 (False Negative) |

**替换组件。** 换一个服务提供商试试。比如网页搜索从 Google 换到 Bing 或 Tavily，RAG 从一个向量库换到另一个。不同引擎在不同场景下差异很大——查询企业营收报表和财务信息时，百度搜索的效果可能远超 Bing 或 Google；但查询学术资源时，结果可能完全相反。这种地域/场景适配只有实际试了才知道，文档里不会写。

## 二、LLM 组件的改进

LLM 组件的改进围绕输入、模型本身、工作流结构三个层面展开，按成本从低到高排序：

### 1. 改进提示词 (Prompt Engineering)

成本最低，见效最快。

**加明确指令。** 在提示词里指明可用的资源和任务应有的规划路径，减少 LLM 自己猜的空间。比如"你可以访问以下三个工具：A、B、C，遇到时间相关的问题先用 A"比"你有工具可用"有效得多。

**少样本提示 (Few-Shot Prompting)。** 在提示词里加几个具体的输入和期望输出示例。LLM 看到示例后会更稳定地复现你想要的格式和风格。比如发票提取的提示词里塞 2-3 张正确提取的发票样本，比纯文字描述规则更管用。

### 2. 尝试不同的 LLM

不同模型擅长的事差别很大。多测几款，用评估指标来选最适合特定任务的模型，别凭偏好拍板。

Andrew Ng 在课程里说他经常试玩新模型，目的是建立"什么模型擅长什么任务"的直觉。aisuite 库（上一节提到的）就是为这个设计的——同一套代码切换不同提供商的模型，快速对比。

### 3. 任务分解 (Task Decomposition)

如果单个步骤的指令太复杂，LLM 执行不稳定，考虑把它拆成更小的步骤。比如把"提取发票所有字段并验证"拆成"提取字段"+"验证字段格式"+"交叉校验日期逻辑"三步，每步一个简单的提示词。

拆分的好处是每步更好调、更好评估；代价是 LLM 调用次数变多，成本和延迟上升。常见组合是"生成步骤 + 反思步骤"——先让一个 LLM 生成，再让另一个（或同一个）反思检查，对应 Module 2 的 Reflection 模式。

### 4. 微调模型 (Fine-Tuning)

这是最复杂、成本最高的选项。只有穷尽前面三种方法后，仍需要挤出最后几个百分点的性能提升时才考虑。

**什么时候才该微调？** 一个简单的决策框架：

| 条件 | 该不该微调 |
|---|---|
| 提示工程能达到目标性能 80% 以上 | 不微调，继续调提示词 |
| 问题只是输出格式/风格不一致 | 不微调，提示词或 Few-Shot 能解决 |
| 高质量标注样本少于 500 条 | 不微调，Few-Shot 更划算 |
| 需要特定领域的深度知识 + 有万级数据 + 有 GPU 资源 | 可以微调 |
| 目标是降低推理成本（小模型微调后匹配大模型效果） | 微调小模型，成本可降 10-50 倍 |
| 数据隐私要求高，数据不能离开本地 | 在自己基础设施上微调开源模型 |

微调的技术方案首推 LoRA（Low-Rank Adaptation）——只训练 1-5% 的参数（在每层加小的适配矩阵），单块 A100 就能训练，原始模型权重保留不变，多个 LoRA 适配器可以叠加。QLoRA 进一步把基础模型量化到 4-bit，Llama 70B 在单块 A100 80GB 上就能微调 [2]。

> 一个常见误区：觉得微调是"终极优化手段"，什么问题都想着微调。实际项目里，提示工程 + RAG + 工具调用能解决绝大多数问题。微调留到方案成熟、性能要求极高、其他方法都试过之后再考虑。

## 三、模型选择直觉

如果你做过类似工作，一定会有一定程度的模型选择直觉——哪个模型擅长什么、什么场景该用谁。这种直觉值钱，能让你在第一时间选对方向，少走弯路。

**不同模型有不同的"性格"。** 以 2025 年下半年的模型为例（模型迭代很快，这些判断会随版本更新变化）：

- **Qwen 比较嘴硬**——让它改东西它会反复强调自己原来的答案没错。这种"嘴硬"在数据报表查询等需要严谨守规则的场景反而是优点，不容易被用户带偏
- **Gemini 2.5 比较逆来顺受**——你说改它就改，配合度高。对一口气生成上千行代码这种任务很在行
- **GPT 言简意赅**——输出紧凑，废话少。Claude 相反，在现有系统里做小范围修改更有心得，能精确改对地方而不重写整个文件
- **DeepSeek 比较有创意和鬼点子**——适合需要发散思维的场景
- **Kimi K2 很有逻辑但容易过度自信**——在中低难度场景能以简短有信服力的输出大放异彩，但复杂场景要做好它过于自信而出错的心理准备

**参数量也影响"情商"。** 大参数模型通常比小参数模型对模糊指令的理解能力更强。一个典型的例子是 GPT-4.5——贵，但在"山东饭局"这种高情商场景下能讲出让人眼前一亮的回复，小模型做不到。新架构 + 大参数量的模型在多步骤复杂指令任务中，能完整列出并编辑所有敏感信息，较小的模型容易出错或遗漏。

> 这些是经验性观察，不是严谨结论。模型每升一个版本，性格可能就变了。直觉要跟着版本更新不断校准。

## 四、直觉怎么培养

模型选择直觉不是天生的，是频繁接触攒出来的。几个具体方法：

**频繁试玩不同模型。** 经常测试新的闭源和开源模型，观察它们在不同查询上的表现。一个可以参考的标准：至少有 3-5 种主力使用的模型（同一提供商只算一次），一个月内至少用过 10 种以上模型，能报出 20 种以上模型的型号。不求数字精确，求的是接触面足够宽。

**建立个人评估集。** 用一套固定的评估任务来校准不同模型的能力——比如准备 5-10 个典型查询（推理题、代码题、改写题、长文档摘要题），每试一个新模型就跑一遍这套题，横向对比。这跟本模块讲的组件级评估是一个思路，只是规模更小、更个人化。

**大量阅读他人的提示词。** 看从业者、专家或开源框架里的提示词，了解不同任务/模型/场景下的最佳实践。Andrew Ng 说他花很多时间读他尊重的人写的提示词，从中学到不少技巧。提示词写得好不好，直接影响模型能力能不能发挥出来。

**在工作流中实际尝试。** 光在 Playground 里试不够，要实际在 Agent 工作流里用。看 Trace 和组件级/端到端评估指标，观察不同模型在特定任务中的性能、价格、速度权衡。Playground 里的表现和工作流里的表现不一定一致——工作流有上下文累积、工具调用、多轮交互，这些都会影响模型发挥。

---

**总结**

- 改进按成本从低到高排序：调参数 → 改提示词 → 换模型 → 任务分解 → 微调
- 非 LLM 组件：调参数（结果数量/阈值/分块大小）+ 换提供商（场景适配差异大，要实测）
- LLM 组件：加明确指令 + Few-Shot 示例 + 多测几款模型 + 复杂任务拆步骤
- 微调是最后手段：提示工程能到 80% 就别微调；500+ 高质量样本 + GPU 资源 + 成熟方案才考虑；LoRA/QLoRA 是主流技术
- 模型选择直觉值钱：不同模型有不同"性格"（嘴硬/配合/言简意赅/有创意/过度自信），大参数模型"情商"更高
- 直觉靠频繁接触攒：主力 3-5 种模型 + 个人评估集校准 + 读他人提示词 + 工作流实际尝试
