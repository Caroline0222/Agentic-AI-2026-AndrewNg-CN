# 更多错误分析示例 More error analysis examples

**核心思想：拿一批失败案例，沿工作流反向追踪，找到出问题最多的那一步。**

上一节讲了错误分析的通用方法——看 Trace、聚焦错误案例、用电子表 格量化每个组件出错频率。这一节用两个具体案例走一遍完整流程，看清"发现问题 → 收集样本 → 定位来源 → 量化决策"每一步到底在做什么。

---

## 一、案例一：发票处理（提取到期日）

这是第一节评估里见过的系统。工作流程如下：

```
发票 PDF → [PDF 转文本] → [LLM 数据提取] → 数据库记录
```

### 发现问题

通过端到端测试，发现整体准确率还不错，但**到期日经常提取错**。这是一个明确的"症状"，但还不知道病根在哪——可能是 PDF 转文本就丢了，也可能是文本对了但 LLM 选错日期。

### 收集错误样本

不要去看那些系统已经正确处理的发票，专注收集 10 到 100 张到期日提取错误的案例。数量不需要特别大，够看出统计规律就行。

### 定位错误来源

对每一张错误发票，逐一检查两个环节的输出：

| 发票 | PDF 转文本是否正确 | LLM 提取是否正确 | 错误原因 |
|---|---|---|---|
| Invoice 01 | 是 | 否 | LLM 把发票日期当成到期日 |
| Invoice 02 | 是 | 否 | LLM 选错日期 |
| Invoice 03 | 否 | — | PDF 文本错误（无法判断 LLM） |
| Invoice 04 | 是 | 否 | LLM 把其他日期当成到期日 |
| Invoice 05 | 是 | 是 | —（标记为不确定） |

这里有个判断标准：**PDF 转文本的输出，人类能不能正确读出到期日。** 如果连人都读不出来，说明问题在 PDF 转文本环节；如果人能读出来但 LLM 选错了，说明问题在 LLM 提取环节。

### 量化指导决策

假设统计 20 个错误案例后发现：

- PDF 转文本错误：4 个（20%）
- LLM 日期抽取错误：15 个（75%）
- 两个环节同时出错：2 个（10%）

注意百分比加起来不是 100%——因为错误**不是互斥**的，一张发票可能两个环节都出问题。

结论很清楚：**LLM 数据提取是主要错误来源，优化重点应该放在 LLM 提示词上**，而不是花几周时间去改进 PDF 转文本组件。

> 如果没有错误分析，团队很可能凭直觉认为"日期识别错误 = OCR 不够准"，然后去换 PDF 解析器、调 OCR 参数、优化图像预处理——几个月下来发现对系统效果几乎没影响，因为真正的瓶颈在 LLM 提取环节。

## 二、案例二：回复客户邮件

这是一个更复杂的工作流，包含多个 LLM 调用和外部系统：

```
客户邮件 → [LLM 编写数据库查询] → 数据库 → [LLM 起草回复] → 人工审核
```

### 发现问题

最终邮件回复质量不令人满意——审核时发现邮件内容跑题、信息缺失、或者语气不对。和案例一一样，"最终输出差"只是症状，真正的病根可能在前面的任何一步。

### 收集错误样本

收集最终回复不满意的客户邮件，同样 10 到 100 封。

### 定位错误来源

这个流程的错误分支更多，每一步都可能是病根：

| 错误来源 | 具体表现 | 判断方法 |
|---|---|---|
| **LLM 查询编写错误** | 生成了错误的 SQL（表名错、条件漏、字段写错），导致取不到客户信息 | 检查生成的 SQL 是否符合数据库 Schema |
| **数据库数据错误** | SQL 正确，但数据库本身的数据是脏的、缺失的、或过时的 | 直接执行 SQL 看返回结果 |
| **LLM 邮件撰写错误** | 信息都对，但邮件语气、措辞、结构不妥 | 对比 LLM 输入的数据和最终邮件 |

每封错误邮件都按这张表过一遍，记录到底是哪一步出了问题。

### 量化指导决策

假设统计发现：

- LLM 编写数据库查询错误：75%
- 数据库数据错误：15%
- LLM 邮件撰写错误：30%

> 百分比加起来超过 100%，因为一封邮件可能多个环节同时出错（查询错了 → 数据库返回空 → LLM 又强行编了一封邮件）。

优先级排序很明确：**先改 LLM 编写查询的方式**（这是 75% 的错误来源），再处理邮件撰写环节。如果先去改邮件撰写的提示词，效果会非常有限——因为很多邮件质量差根本不是撰写环节的问题，是上游数据就错了。

## 三、两个案例的共性

| | 案例一：发票处理 | 案例二：回复客户邮件 |
|---|---|---|
| 工作流组件数 | 2（PDF 转文本 + LLM 提取） | 3（LLM 查询 + 数据库 + LLM 邮件） |
| 错误来源数 | 2 | 3 |
| 量化结果 | LLM 提取占 75% | LLM 查询占 75% |
| 决策 | 优化 LLM 提示词 | 先改查询生成，再改邮件撰写 |
| 反直觉点 | 直觉会怪 OCR | 直觉会怪最终邮件撰写 |

两个案例都印证了同一个道理：**表面上的错误位置，往往不是真正的错误来源。** 最终输出错，可能是上游组件造成的；邮件质量差，可能是 SQL 查询早就错了。沿工作流反向追踪，才能找到真正的瓶颈。

---

## 四、错误归因的三个坑

实际操作时，有几个容易踩的坑要避开：

**坑一：把所有错误归因于模型。** 这是初学者最常见的反应——Agent 结果不对，第一反应是"模型不够强"。但实际链路里，PDF 转文本、数据库脏数据、工具调用错误、上下文丢失，每一个环节都可能让最终结果跑偏。先沿链路反向追，别急着换模型。

**坑二：只看最终输出，不看中间步骤。** 端到端评估能告诉你"系统成功率是 82%"，但无法直接告诉你"剩下 18% 为什么失败"。必须拆开看每个组件的输出（Trace 和 Span），才能定位病根。

**坑三：错误样本太少或选偏了。** 10 到 100 个错误样本是起步规模，太少了看不出统计规律。同时要确保样本覆盖各种错误类型，别只挑同一种错误的案例——那样统计出来的错误分布会失真。

---

## 五、完整的优化闭环

把前两节的方法串起来，一个成熟的 Agent 工作流优化过程形成这样的闭环：

1. 建立端到端评估（End-to-End Evaluation），知道整体表现
2. 收集失败案例（Focus on Failures），10 到 100 个
3. 做错误分析（Error Analysis），拆开看每个组件的输出
4. 统计各组件的错误贡献（Component Fault Attribution）
5. 找出最高优先级的错误来源（Prioritize）
6. 针对该组件建立组件级评估（Component-level Evaluation）
7. 优化该组件（Component Optimization）
8. 回到端到端评估，验证整体是否提升

```
端到端 Eval → 错误分析 → 组件级 Eval → 组件优化 → 端到端 Eval
    ↑                                                    |
    └────────────────────────────────────────────────────┘
```

这个闭环比"不断改 Prompt，然后看效果有没有变好"要科学得多。下一节会展开讲组件级评估——为什么端到端评估不够、组件级评估怎么建、它跟错误分析怎么配合。

---

**总结**

- 错误分析的核心是**沿工作流反向追踪**，定位哪个组件出错最多，而不是凭直觉猜
- 错误样本**不是互斥**——一张发票可能两个环节都错，百分比加起来会超过 100%
- **表面错误位置不等于真正的错误来源**——最终输出错可能是上游造成的，先反向追再动手改
- 10 到 100 个错误样本是起步规模，覆盖各种错误类型才有统计意义
- 完整优化闭环：端到端评估 → 错误分析 → 组件级评估 → 组件优化 → 回到端到端验证
